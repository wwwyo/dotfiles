# Memo

`~/src/github.com/wwwyo/me/daily/<today>/memo-<topic>.md` に、概念ごとのメモを作成・追記するスキル。

カレントディレクトリがどこであっても、`wwwyo/me` の今日のディレクトリへ書き込む。これは知識をハブに集約するための明示的な設計（`wwwyo/me/AGENTS.md` 参照）。

## 設計の前提

同じ概念の続きは同じファイルへ追記し、概念が異なる内容は新しい `memo-<topic>.md` に分ける。1ファイルを開けば、その概念の議論をまとめて読める単位にする。

名前は内容を表す短い kebab-case（例: `memo-agent-models.md`）。日付はディレクトリにあるのでファイル名に重ねない。既存の `memo.md` も参照し、同じ概念の続きやユーザーがそのファイルを指定した追記には使える。

## 実行フロー

### 1. 入力ソースを決める

ユーザーの起動方法によってメモ内容のソースを決める:

- `/memo <内容>` のように引数あり — 引数をそのまま本文の素材にする
- `/memo` 単独 or 直前に議論があった場合 — 直前の会話・議論からエッセンスを抽出する。垂れ流しの議事録ではなく、後で見返したときに価値があるよう 示唆・判断・気づき に絞る
- ユーザーが追加情報を持っている場合 — 「補足ある？」と一度だけ短く聞く。なければそのまま進む

迷ったら「これをメモする方向でいい？」と一言確認。長い質問はしない。

### 2. 概念に合うファイルを選ぶ

当日の `memo.md`・`memo-*.md` を読み、今回の問いや議論の対象が既存のメモと同じか判断する。非公開の内容なら `.local.md` のメモも対象にする。

- 同じ概念の続き・補足・訂正なら、既存ファイルへ追記・修正する。見出しが違うだけでは分けない
- 別の概念なら、新しい `memo-<topic>.md` を作る。同じ名前が既にあって内容が異なる場合は、概念の違いが分かる名前にする
- 複数の独立した概念を一度にメモするときは、それぞれのファイルに分ける
- ユーザーがファイル名・追記先を明示した場合は、その指定を優先する

例: Atomic の事業分析と agent のモデル設定は別ファイル。agent のモデル設定に Pullfrog の指定を補足するなら、同じ `memo-agent-models.md` に追記する。

### 3. 見出しと本文を整形する

見出し: `## HH:MM <短いトピック>` 形式。HH:MMは現在時刻（24時間制、JST）。トピックは10〜30文字程度で内容が一目で分かるもの。

本文: 箇条書きでも段落でもよい。ただし以下を意識する:

- 何が起きた / 何を考えた / 何が分かった を簡潔に書く
- 元発言の引用は最小限。要約優先
- 関連リンク（GitHub issue/PR、記事URL、ファイルパス）があれば末尾にまとめる
- 後日 wiki 化される可能性があるなら、wiki 化したい論点を明記する（例: `→ wiki化候補: XXX について`）

GitHub の issue/PR 番号は必ず `[owner/repo#123](https://github.com/owner/repo/issues/123)` 形式でリンク化する。裸の `#123` は禁止（`wwwyo/me` 全体のルール）。

### 4. ファイルへの書き込み

書き込み先: `~/src/github.com/wwwyo/me/daily/$(date +%F)/memo-<topic>.md`（step 2 で既存ファイルを選んだ場合はそのファイル）。

社外秘・社内限定の内容（顧客名を伴う案件の見積もり・金額・社内の意思決定・人事や体制の話）は `memo-<topic>.local.md` に書く。`.gitignore` の `*.local.*` で git 管理外になる。公開できる内容と社内限定の内容が両方あるなら、`memo-<topic>.md` と `memo-<topic>.local.md` を並置して書き分ける（`wwwyo/me/AGENTS.md` のファイル命名規約）。既存の `memo.local.md` を選んだ場合も同じ扱い。

**先に `.local` かどうかを判断してから書く。** 判断を誤って公開用のメモに書いてしまった場合、`git mv` でリネームしても**中身は git 履歴に残る**（`.gitignore` は追跡済みファイルには効かない）。未 commit なら単にファイル名を変えるだけでよい。既に commit してしまったら、未 push であることを確認したうえで `git reset --soft` でコミットを戻し、`git restore --staged <file>` で未追跡に戻す（ファイル自体はディスクに残る）。push 済みなら履歴の書き換えが必要になるので、ユーザーに判断を仰ぐ。

#### 4-1. 今日のディレクトリがない場合

```bash
mkdir -p ~/src/github.com/wwwyo/me/daily/$(date +%F)
```

`/daily-start` を先に走らせるべきか迷うこともあるが、memoはdaily-startを待たない。先に書いて構わない。daily-startが後から走ってもファイルは共存できる。

#### 4-2. 選んだメモがまだない場合

新規作成。先頭に日付見出しは付けない（ディレクトリ名が日付なので冗長）。最初のエントリだけを書き出す:

```markdown
## HH:MM <トピック>

<本文>
```

#### 4-3. 選んだメモが既にある場合

ファイル末尾に `---` 区切り + 新エントリを追記する:

```markdown
（既存内容）

---

## HH:MM <トピック>

<本文>
```

末尾の改行に注意。既存ファイルの最終行が改行で終わっていないと区切りが崩れるので、必要なら改行を補う。

### 5. 完了報告

書き込んだファイルパスと、追記した見出しを1〜2行で報告する。長い解説はしない。

例:
```
daily/2026-04-28/memo-ddd-cohesion.md に「14:32 DDD実装の凝集度トレードオフ」を作成しました。
```

## やらないこと

- 同じ概念の続きに、呼び出しごとに新しいファイルを作らない
- wikiへの直接書き込みはしない — wiki化は `/daily-end` の中で議論して判断する。memoは raw source（ソース層）であり、wikiは合成層
- 長文の議事録化はしない — 後で読み返して価値がある示唆に絞る。冗長なメモは振り返りの邪魔になる
- 過度な確認をしない — 「これメモっていい？」を毎回聞かない。明らかにメモ用途で呼ばれているなら黙って書く

## エッジケース

- 複数トピックを一気にメモしたい — 概念ごとにファイルを選ぶ。同じファイル内に複数の `## HH:MM ...` セクションを置く場合は `---` で区切る
- 誤って書いた / 直したい — 対象のメモを直接修正する。スキルを再実行しない
- 日跨ぎ（深夜0時を回った）— `date +%F` の結果に従う。日跨ぎでまとめて書きたい場合はユーザーに確認
- wwwyo/me が見つからない — `~/src/github.com/wwwyo/me` が存在しない環境では使えない。エラーで `wwwyo/me リポジトリが見つかりません` と伝える
