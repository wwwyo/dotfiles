# QA Execution 型

テスト実行時の実務知見（環境準備・UI で作れない状態の再現・判定・記録）を持つ型。コードにもチケットにも残らない「どこで詰まってどう抜けたか」を構造化する。テスト設計・ケース作成そのもののプロセスは対象外 — この型は実行時に限定する。

## いつこの型か

- テスト実行中に繰り返し詰まる手順（環境準備・特殊な状態の再現・バグか期待値かの判定・記録の同期）を持たせたいとき選ぶ
- テスト設計・ケース作成のプロセス標準は別のチーム/共有 skill の対象。実装機構の規約は [guideline 型](guideline.md) が対象

## SKILL.md の routing 骨格

| Mode | やること | 読む reference |
| :--- | :--- | :--- |
| **Setup** | ログイン・テストアカウント・環境準備 | setup |
| **Reproduce** | UI では作れない状態（エラー・競合・連打等）を作る | reproduce |
| **Rule-change** | ルール変更（承認要否・権限等）を変えて検証する | rule-change |
| **Judge** | バグか期待値かを確定する | judge |
| **Domain** | 判定がどの区分（例: 事前定義済みか実行時生成か）に基づくかを見極める | domain |
| **Record** | 結果記録・集計の同期・成果物反映 | deliverables |

複数 mode にまたがるときは Domain → Reproduce → Judge → Record の順が自然。

## references の切り方

1 reference = 1 mode。環境操作・特殊状態の再現手順・ルール変更検証・バグ判定基準・ドメイン判定・記録と集計同期に分ける。

## tools / evals

lint は持たず、決定論的に集計できるものだけ `tools/` に置く（例: 複数箇所に散った集計値を 1 コマンドで同期するスクリプト）。判断（バグか期待値か等）は tool 化せず reference に残す。evals は持たない — 実行時の詰まりどころは題材ごとに異なり、固定した正解での汎化測定に向かない。

## governance

都度還元 — テストを回して得た非自明な発見をその場で該当 reference に追記する。一度きりの操作・自明な手順は書かない。新しい mode が要るほど大きい塊が出たら reference を追加し SKILL.md の Mode routing に 1 行足す。決定論的に検証できるものが見つかったら `tools/` に足す。evidence 源はテスト実行そのもの（詰まった箇所とその回避策）。
