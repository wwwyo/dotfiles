# Investigation 型

不具合・問い合わせの原因調査を、推測でなくログの実数（実態）とコード（原因）で詰めるための汎用手順を持つ型。ドメイン固有の特化知識だけを分離する。

## いつこの型か

- 「なぜ起きたか」を事実で詰める調査の型（症状の翻訳 → 実態の観測 → コードでの原因特定 → 仮説の検証）を持たせたいとき選ぶ
- 実装機構そのものの規約は [guideline 型](guideline.md)、UI/UX の判断は [product-design 型](product-design.md) が対象。調査中に見つかった実装規約の逸脱は guideline 型の reference に還元し、この型には残さない

## SKILL.md の routing 骨格

mode 表は持たない。入口（症状の種類ごとの始め方）＋ 調査の型（共通の手順）＋ 落とし穴チェックリストを SKILL.md 本体に書き、ドメイン固有の特化知識だけを reference に切り出す。

```markdown
## 入口別の始め方
### A. （症状の種類 1）
- （どこから何を特定するか）
### B. （症状の種類 2）
- （どこから何を特定するか）

## 調査の型（共通）
1. 症状を観測可能な単位に翻訳する
2. 実態を記録・可観測性の基盤（ログ等）で取る → references/<観測基盤>.md
3. コードで原因を読む
4. 仮説を検証可能な形にして潰す

## 落とし穴チェックリスト（ドメイン非依存）
- [ ] …

## ドメイン別の特化知識（`references/domains/`）
- **（ドメイン名）**: `references/domains/<name>.md`
- 今後ドメインが増えたら `references/domains/<name>.md` を足し、ここに1行で登録する。汎用フロー（このファイル）は変えない
```

## references の切り方

汎用の観測基盤の使い方（クエリの組み方・落とし穴）を1つの reference に持ち、ドメイン固有知識は `references/domains/<name>.md` に 1 ドメイン 1 ファイルで切る。SKILL.md 本体（入口・調査の型・チェックリスト）は reference 化しない — 全案件で毎回読む共通手順のため。

## tools / evals

どちらも持たない。調査の検証手段はログ・コードそのもの（観測基盤への問い合わせ手順は reference 内のクエリテンプレとして持つ）であり、決定論チェックに落とせる対象がない。判断の汎化を測る evals も対象外 — 調査は毎回対象システムの状態が異なり、正解を固定した題材で汎化を測れない。

## governance

新しいドメインの特化知識が増えたら `references/domains/<name>.md` を追加し SKILL.md の一覧に 1 行登録する。汎用フロー（症状の翻訳・実態の観測・コードでの原因特定・仮説検証）自体は変えない。evidence 源は個々の調査そのもの（問い合わせ・障害・CI 失敗の実例）で、随時 reference に還元する。
