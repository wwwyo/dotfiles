# リサーチ結果レポート（research）

技術調査・比較検討・事実確認など「問いに答える調査」のレポート型。型に共通するルールは `../SKILL.md` の「構成の型」に従う。

## 並び順

読者が知りたい順（結論・意思決定に近い問いから）。調査を実行した順・ソースを読んだ順にしない。

## 構成

- header のリード: 調査の問いと答えの要約を 1〜2 文で書く
- section = sub-question / テーマ単位
- finding は箇条書き = 主張文。確度が低いものは主張文の直後（`[n]` の前）に `（未確認）` `（1 source のみ）` のような表記を付ける。確かなものは無印でよい（全件に一律表記しない）
- 出典は `<a href="#src-1">[1]</a>` のように番号で参照し、末尾の Sources section と対応させる

## 矛盾・不一致

ソース間で主張が食い違うときは `.state-table.compare`（反映前/反映後の色を付けない variant）で対立を並べる:

| | 説 A | 説 B |
| --- | --- | --- |
| 論点 | 主張 [n] | 主張 [n] |

採る説（または判断不能）を 1 bullet で添える。

## 比較調査

技術選定・ライブラリ比較など選択肢を比べるときは decision matrix（`.state-table.compare.matrix`）にする:

| 観点 | A | B | 採用 |
| --- | --- | --- | --- |

行 = 比較観点。「採用」列はその観点で優位な方を書き、**必ず最終列に置く**（`.matrix` が最終列を強調するため。選択肢が 3 つ以上あっても列数に関係なく効く）。違いのない観点は書かない。表だけだと行ごとの勝者しか見えないので、表の直後に全体の結論（どれを採るか・決定要因）を 1〜2 bullet で添える。

## 末尾に必ず置く

- **わからなかったこと**: 確認できなかった・情報が見つからなかった項目を箇条書き。隠さない
- **Sources**: `[n]` + タイトル + 出典 + 種類（公式 docs / 一次資料 / 記事 等）が分かる補足。出典は URL とは限らない — ローカルコードを読んだ調査なら `path/to/file.ts:123` や commit SHA、社内ドキュメント名など**読者が辿れる形**で書く。**読者が非エンジニアでも省略しない** — 出典は調査の信頼性の本体であり、「識別子を本文に書かない」ルールの例外（`[n]` 参照も同様）

この 2 つの section 名（「わからなかったこと」「Sources」）は固定ラベルとして使う。「見出しは文にする」ルールの例外とする（内容ではなくセクションの種類を示す名前のため）。
