# ドキュメント共同作成

README、設計書、提案書、技術仕様、意思決定文書などを作るときに使う。

## 基本方針

- フォーマット（DesignDoc / README 等）の構成・粒度・セクション分けは、既存の類似文書（precedent）の体裁を真似ず、この skill の `assets/` テンプレートと `references/` ガイドラインに従う。
- 内容の参考になる既存文書があれば先に読む（ただし体裁の基準は上記の通りガイドライン優先）
- 必要以上にプロセスを強制しない

## ドキュメントガイドライン

フォーマットによらず、ドキュメント全般に共通する書き方と出力の指針。文章の規範は `japanese-tech-writing` skill に従う。文書構造は本ファイルに従う。

### 技術ドキュメントの書き方

- 見出しは技術用語やコンポーネント名ではなく、達成したい目的で書く
  - Bad: 「Microsoft Graph Subscription 管理」「Webhook 受信処理」
  - Good: 「ユーザーがカレンダーを連携したときにWebhook監視を開始する」「Webhookの取りこぼしを定期的に補完する」
- 具体的な実装コード（関数の中身、APIリクエスト例など）は書かない。フォーマット固有の例外は、対応する `references/` ガイドラインに従う
- ただし model の interface、DB schema、proto schema など、コンポーネント間の契約を定義するものは書く

### 図（mermaid）の扱い

- 複雑な概念・構造・フローは、本文に入る前に mermaid 図で全体像を示す。読み手が細部を読む前に俯瞰を持てる
- フロー・状態遷移・依存関係・アーキテクチャなど、文章で追うより図が速い対象に mermaid を使ってよい

### table の扱い

- セル内に長文が入るときは table を使わない（横に伸びて読みにくい）。構造を示したいだけなら箇条書きにする。table は比較（観点 × 案などの属性比較）のときだけ使う

## 進め方

### 1. 枠組みを決める

最初に文書の枠組みを決める。

- どんな文書か
- 誰が読むか
- 読後に何を決める、理解する、実行するべきか
- 制約、締切、前提条件

テンプレートや既存文書があるなら読み込む。

### 2. フォーマットを選ぶ

定義済みフォーマットが合うなら使う。フォーマットを使う場合は、着手前に対応する `assets/` テンプレートと `references/` ガイドラインの両方を必ず読むこと。これは必須で、読まずに記憶や precedent の体裁で構成を組み始めてはいけない。

- DesignDoc: テンプレート `assets/design-doc.md` ／ ガイドライン `references/design-doc.md`
- README: テンプレート `assets/readme.md` ／ ガイドライン `references/readme.md`
- PRD: `prd` スキルを参照
- AGENTS.md（repo 起動時 index）: テンプレート `assets/agents-md.md` ／ ガイドライン `references/agents-md.md`
- それ以外はカスタム

フォーマットが合わないなら無理に当てはめない。

### 3. 必要な情報を集める

会話・対象 repo・資料から必要な情報を集める。未確定の設計判断や用語を詰める必要があるときは `grill-with-docs` を使う。材料が揃っている文書作成や軽微な修正ではヒアリングを追加しない。

### 4. ドキュメント化する

集めた情報を、選んだフォーマットの `assets/` テンプレートと `references/` ガイドラインに沿って文書として書き上げる。

### 5. codex にレビューを依頼する

書き上げたら、[delegate](../delegate/SKILL.md) の Codex reference を使い、次の2つを別々のレビューとして依頼する。文章面と技術面を分けると、観点が混ざらず各々を深く見てもらえる。

1. 文章の正しさ

- 該当の `assets/` テンプレート・`references/` ガイドラインに沿っているか
- `japanese-tech-writing` skill に沿っているか
- 冗長な段落やリンクの不正確さがないか

2. 内容の技術的確からしさ

- 主張・設計・判断が技術的に妥当か
- 事実・技術詳細が正確か

読者テストは、高リスクな文書や誤読コストが高い文書でのみ任意で行う。

### 6. レビュー指摘を反映する

レビューの指摘を文書に反映する。反映しないと判断した項目はユーザーに提示する。反映が大規模な変更になったら、5 のレビュー依頼に戻って再レビューする。
