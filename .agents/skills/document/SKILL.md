# ドキュメント共同作成

README、設計書、ADR、提案書、技術仕様、意思決定文書などを作るときに使う。

## 基本方針

- 文書の構成は、この skill の `assets/` テンプレートと `references/` ガイドラインに従う。
- 関連する既存文書は内容の参考にする。構成は上記のテンプレートとガイドラインを優先する。
- 必要以上にプロセスを強制しない

## ドキュメントガイドライン

以下は、文書全般に適用する。日本語の文章は `japanese-tech-writing` skill も参照する。文書構造は本ファイルに従う。

### 簡潔で明確に書く

すべての文書で [ASD-STE100](https://www.asd-ste100.org/about.html) を80%程度意識する。
80%は、この skill での取り入れ方の目安であり、公式の準拠率ではない。
英語では簡潔な語彙と文構造を使う。日本語の明確さの原則は `japanese-tech-writing` skill を正本とし、文書には特に次を適用する。

- 手順は1ステップにつき1つの操作を示す。条件は、その条件がかかる操作の前に書く。
- 資料にない実行者を補わない。
- 専門用語は初出で説明し、API 名やコマンド名は正確に保つ。

語彙制限や語数制限を機械的に当てはめない。正確さと自然な文章を優先する。
この skill 自身の説明、各ガイド、テンプレートの記入案内にも同じ方針を使う。

### 技術ドキュメントの書き方

- 見出しは、その節の目的や答える問いが分かる表現にする。技術用語だけを並べない。
  - Bad: 「Microsoft Graph Subscription 管理」「Webhook 受信処理」
  - Good: 「ユーザーがカレンダーを連携したときにWebhook監視を開始する」「Webhookの取りこぼしを定期的に補完する」
- 関数の中身や API リクエスト例など、具体的な実装コードは原則として書かない。形式ごとの例外は `references/` に従う。
- インターフェースやデータ構造など、コンポーネント間の契約は必要に応じて示す。

### 図（mermaid）の扱い

- 複雑な概念・構造・フローは、詳細の前に mermaid 図で全体像を示す。
- フロー・状態遷移・依存関係・アーキテクチャなど、文章で追うより図が速い対象に mermaid を使ってよい

### table の扱い

- 表は、選択肢や属性を比較するときに使う。構造を示すだけなら箇条書きにする。
- セルが長文になる場合は、説明を本文へ移す。

## 進め方

### 1. 枠組みを決める

最初に文書の枠組みを決める。

- どんな文書か
- 誰が読むか
- 読後に何を決める、理解する、実行するべきか
- 制約、締切、前提条件

テンプレートや既存文書があるなら読み込む。

### 2. フォーマットを選ぶ

定義済みの形式が合うなら使う。着手前に、対応する `assets/` テンプレートと
`references/` ガイドラインの両方を読む。記憶や既存文書だけを基に構成を決めない。

- DesignDoc: テンプレート `assets/design-doc.md` ／ ガイドライン `references/design-doc.md`
- ADR（設計判断の記録）: テンプレート `assets/adr.md` ／ ガイドライン `references/adr.md`
- README: テンプレート `assets/readme.md` ／ ガイドライン `references/readme.md`
- PRD: `prd` スキルを参照
- AGENTS.md（repo 起動時 index）: テンプレート `assets/agents-md.md` ／ ガイドライン `references/agents-md.md`
- それ以外はカスタム

フォーマットが合わないなら無理に当てはめない。

### 3. 必要な情報を集める

会話・対象 repo・資料から必要な情報を集める。
設計判断や用語が未確定なら `grill-with-docs` を使う。
材料が揃っている場合や軽微な修正では、ヒアリングを追加しない。

### 4. ドキュメント化する

集めた情報を、選んだフォーマットの `assets/` テンプレートと `references/` ガイドラインに沿って文書として書き上げる。

### 5. codex にレビューを依頼する

書き上げたら、[delegate](../delegate/SKILL.md) の Codex reference を使い、次の2つを別々のレビューとして依頼する。文章面と技術面を分けると、観点が混ざらず各々を深く見てもらえる。

1. 文章の正しさ

- 該当の `assets/` テンプレート・`references/` ガイドラインに沿っているか
- `japanese-tech-writing` skill に沿っているか
- ASD-STE100 を80%程度意識した共通方針に沿っているか。長文、用語の揺れ、曖昧な主語を確認する
- 短くした結果、必要な前提・条件・例外・判断理由が抜けていないか
- 冗長な段落やリンクの不正確さがないか

2. 内容の技術的確からしさ

- 主張・設計・判断が技術的に妥当か
- 事実・技術詳細が正確か

読者テストは、高リスクな文書や誤読コストが高い文書でのみ任意で行う。

### 6. レビュー指摘を反映する

レビューの指摘を文書に反映する。
反映しない項目がある場合は、その項目をユーザーに示す。
大規模な変更になった場合は、5 に戻って再レビューする。
