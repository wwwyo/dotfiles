# README ガイドライン

README は、読者が使う理由を理解し、最初の利用や開発を始める入口にする。
用途と手順に加えて、その製品を選ぶ価値を伝える。
詳細は別の文書に分け、最初に必要な情報を見つけやすくする。

テンプレートは `assets/readme.md`。見出しと順序は出発点とし、読者に不要な節・プレースホルダーは完成時に削除する。
文章は [共通方針](../SKILL.md#簡潔で明確に書く) に従う。

## できるだけ短くする

README は短いほどよい。使う理由、価値が分かる実例、試す導線を最小限の文章で伝える。説明を追加する前に、削除・統合・詳細資料へのリンクで済むかを考える。

- 概要と実例で価値が伝わるなら、独立した特徴一覧や「使う理由」の節を足さない。同じ内容を概要・箇条書き・画像説明で繰り返さない
- 詳細なセットアップ、API 仕様、設計、開発・運用手順、FAQ は `docs/` や既存の資料へ分ける。README には最初の利用に必要な最短の手順か、その手順への直接リンクを残す
- ロゴ・バッジ・デモも数と表示サイズを絞る。網羅的な機能紹介や装飾で縦に長くしない
- 削った結果、使う理由や次の行動が分からなくなるなら、その情報は残す

## 読者と最初の行動を決める

- 主要読者を利用者か開発者か決め、その人が最初に達成することを一つ選ぶ。両方を扱うなら、利用者向けの導入と開発環境のセットアップを区別する
- 利用者向けの導入に、開発 repo や執筆者個人のツール管理方式を必須条件として持ち込まない。個人のバージョン固定やリリース後の待機期間も要求しない
- 通常の操作例は `<command>` を基本にする。`mise exec -- <command>` などは、その方式を使う場合の例として示す
- AI 向けの `docs/start.md` も、利用者や導入先のツール管理方式と規約に従う
- CLI をグローバルに導入できる場合は、導入先 repo のツール設定を増やす手順を前提にしない。開発者向けには repo が採用する方式を記載してよい
- 言語はプロジェクトの基準言語と主要読者に合わせる。日本語を基準にするチーム向けなら、日本語の `README.md` でよい
- 公開アプリならアクセス先、CLI なら導入と最初のコマンド、ライブラリならインストールと短い利用例を先に示す
- 社内サービスなら開発・運用担当者の起動や検証を優先してよい。資料・設定集なら、資料の探し方や設定の適用方法を示す。用途のないインストール節を作らない
- サブディレクトリの README は、そのディレクトリの役割・使い方・関連資料を扱い、ルートの説明を重複させない

### 英語を基準にするプロジェクト

- 英語の `README.md` を正本とし、日本語版の `docs/README.ja.md` も作る。両方を短く保ち、価値の説明・利用手順・制約を揃える
- 冒頭の主要リンクに言語切替を含める。英語版から `[日本語](docs/README.ja.md)`、日本語版から `[English](../README.md)` へ相対リンクする
- 内容を変えるときは同じ変更で両方を更新する。コマンド、設定名、URL、バージョンなどの技術情報は一致させ、説明文は自然な日本語にする
- 日本語版の画像・repo 内リンクは `docs/` からの相対パスに直す。英語版のパスをそのまま複製しない

## 使いたくなる理由を具体化する

書く前に、想定読者の困りごと、利用後に得られる結果、このプロジェクトを選ぶ理由を整理する。機能名を並べるだけでなく、読者の作業がどう変わるかを説明する。

- 概要は、読者の課題、得られる結果、その結果が分かる実例、試す導線の順に理解できる構成にする。バッジの下でコンセプトを短く説明し、長い操作説明の前に試す価値が分かるようにする
- 代表的な利用場面を一つ見せる。CLI なら入力と出力、ライブラリなら短い利用コードと結果、UI なら実際の操作と画面で、価値を確かめられるようにする
- 利点は具体的な変化として書く。「多機能」より「CSV を渡すと集計表まで生成できる」のように、できることと得られる結果を対応させる。この例は表現の型であり、実在しない機能を補う根拠にはしない
- コンセプトは、利用者が何をできるようになるかを中心に書く。記録・追跡・保存などの仕組みを主役にせず、その価値を支える手段として説明する
- 既存のやり方や代替ツールから選び替える理由があるなら示す。比較は対象・条件・根拠を揃え、確認できない優位性や数値を作らない。明確な優位性がなくても、特定の用途との相性を説明できる
- 「デモを試す」「最初のコマンドを実行する」など、読者にしてほしい次の行動を一つ目立たせる。文書・コミュニティ・スポンサー等のリンクを同じ強さで大量に並べない
- 利用判断に必要な制約は見える位置に残す。向いている用途と重要な非対応事項を示し、使い始めてから期待との違いに気付く構成を避ける

## 書く前に実態を確かめる

既存の README と関連文書を読み、宣言と実装の両方で内容を確認する。

- マニフェスト、ロックファイル、ツール設定、タスク定義から、対応環境・依存・起動・検証コマンドを調べる。開発環境の手順は repo のツール管理方法に合わせる
- 設定例とコードから、必須の設定項目と認証情報の取得・設定方法を確認する。秘密の値は載せない
- CI、リリース設定、LICENSE、CONTRIBUTING.md、設計資料から、実在する手順・条件・参照先を確認する
- 実装済み・実験中・予定を区別する。未確認のコマンド、対応バージョン、ライセンス、窓口を補って埋めない。必要な事実が不明なら確認し、推測を公開文書の事実にしない
- 既存 README の改善では、利用判断に必要な情報と有効な導線を保つ。節や資料を移す場合は参照元も確認し、リンクを更新する

## 冒頭で利用判断を助ける

冒頭は、ロゴ、バッジ、主要リンク、短いコンセプト説明の順にする。
ロゴにサービス名が含まれる場合は、同じ名前の見出しを重ねない。名前がない場合は見出しで補う。
コンセプトには、誰のどんな課題を解決し、何ができるかを書く。
機能の全列挙や技術スタックの一覧から始めない。

- 本文の前に、主要リンクを短い列で置く。Web サイト・ダウンロード・ドキュメント等から、実在する導線を選ぶ。英語を基準にする場合は「日本語」も含める
- 代表的な用途を具体的に示す。「高速」「簡単」などの評価語だけで利点を説明しない
- 導入手順の前に、解決する困りごとと製品の考え方を短く説明する。「使う」という節で操作や内部管理の仕組みを長く列挙しない。具体的な使いどころを示し、コマンドの詳細は利用者向けの文書に分ける
- 特徴を挙げる場合は、読者が選ぶ理由になる少数の利点に絞り、詳しい説明へリンクする。性能比較を載せるなら測定条件と根拠も示す
- `Features` は利用者が得られる結果を書く。コマンド・処理・管理方式の列挙にせず、「何ができるようになるか」「何を保てるか」「何が分かるか」を具体的に示す
- 各 feature は「短い見出し＋絵文字: 詳細」の形にする。見出しは得られる価値を表し、詳細はその結果を1文で説明する
- 実験段階、保守終了、利用対象の限定、重要な非対応事項があれば、読者が試す前に見つけられる位置に書く
- UI や出力を見せるほうが用途を伝えやすい場合は、スクリーンショットや短いデモを添える。画像には内容を説明する代替テキストを付ける

## 最初の利用を完了できる手順にする

「使い始める」には、前提、導入、必要な設定、代表的な操作、成功の確認までを順に書く。

README では共通ガイドラインの実装コード制限の例外として、最初の利用に必要な実行コマンド・短い利用コード・API リクエスト例を載せてよい。内部実装の説明は詳細資料に分ける。

- コマンドは実行ディレクトリと前提を明示し、コピーして実行できる形にする。プロンプト記号を混ぜず、コードブロックに言語を指定する
- ライブラリでは公開 API を使う最小のコード例、API サービスでは最初のリクエスト例を載せてよい。入力と期待する結果を対応させる
- 設定値のプレースホルダーは置換する箇所と取得元を説明する。秘密は repo の既定の管理方法で設定させる
- 利用者に不要なビルドやソースからの起動を要求しない。選択肢が多い場合は基本手順を一つに絞り、環境別の詳細をリンクする
- 手順が長ければ、初回に不要な操作を詳細資料へ分ける。必要な前提や設定を省いて短く見せない
- インストール不要のデモや Playground が実在するなら、冒頭から試せるようにする。ローカル利用の手順も辿れるようにする

## AI agent に導入を任せる製品

AI agent に製品の導入を任せる場合は、独立した手順 `docs/start.md` を用意する。
CLI や開発ツールで、agent skill も導入する製品に適用する。
README は次の順にする。

1. ロゴ・バッジ・主要リンクの下に、コンセプトを書く。
2. `## QuickStart` に、手順の URL を読ませる prompt を置く。
3. `### Manual` に、短い手動手順を書く。
4. `## Features` に、得られる結果を書く。
5. 採用するライセンスがある場合は、最後に `## License` を置く。

「AI に導入を任せる」という別の節は作らない。

- `docs/start.md` はこの文書だけで導入を完結させる。CLI 本体に加えて製品が agent skill を持つ場合は、skill の取得・配置・必要な依存・agent が読み込めたことの確認までを含める
- prompt には、手順の URL と対象 repo への導入意図を書く。特定の製品名やサービス名を共通規約に固定しない
- `QuickStart` の prompt と、自分で実行する人向けの `Manual` の両方を残す。手動手順は必要な前提と最短のコマンドに絞る
- `docs/start.md` は AI 向けの手順として扱い、README の手動導入から人間向けの詳細ガイドとして案内しない。手動導入に必要な説明は README か利用者向けの文書に置く
- AI 向けの `start.md` と runtime の agent skill（SKILL.md）で導入手順を重複させない。SKILL.md は導入後の操作だけを扱い、`start.md` と同じ製品導入手順の節を持たせない。ただし「現在の cwd で動く」ような日常操作の契約は簡潔に残す

prompt の例:

```text
Read https://raw.githubusercontent.com/<owner>/<repo>/main/docs/start.md and install the CLI and skill in this repository.
```

## OSS の実例から構成を選ぶ

実例の見た目だけを真似ず、読者が何を判断し、どこから試せるかを参考にする。

- CLI・開発ツールは uv のコマンドと出力の見せ方を参考にする。README には代表例を一つ残し、用途別の例や性能比較の詳細はリンク先へ分ける
- UI・対話型アプリは marimo 型を参考にする。ロゴと主要リンク、操作が分かるデモ、すぐ試せる入口、ローカルでの Quickstart を組み合わせる。画像・動画の数は用途が伝わる範囲に絞る
- ドキュメントサイトが充実している場合は shadcn/ui 型を参考にする。概要と代表画像、利用ドキュメント、貢献ガイド、ライセンスへの案内だけで短くまとめてもよい。その場合、最初の利用手順への直接リンクを用意し、README とサイトで手順を二重管理しない
- 雛形を使う場合は、生成後に repo 名、バッジの対象、リンク、ライセンスを実態に合わせる。cookiecutter-uv のような初回セットアップの説明は、作成者向けの手順と継続的な利用・開発手順を区別する

## 詳細資料と開発者向けの導線を置く

README には最初の行動に必要な情報を残し、繰り返し参照する詳細は適切な文書へリンクする。短いプロジェクトなら本文で完結してよく、存在しない文書へのリンクのために分割しない。

- 利用者向けには、手順を追うチュートリアルと、仕様を調べるリファレンスを区別する
- 開発者向けには、セットアップ、ローカル起動、既存のテスト・lint・ビルド、最小限の動作確認を示す。長い手順や貢献ルールは CONTRIBUTING.md 等へ案内する
- 設計・構成は設計資料へ、変更履歴と更新時の対応は CHANGELOG や Releases へ、運用・デプロイは手順書へ案内する。README 本文には現在の利用方法を保ち、一時的な移行記録を溜めない
- 問い合わせ先と不具合報告方法を明示する。公開プロジェクトならライセンスと保守主体への導線も確認する。ライセンスが見当たらなければ勝手に選ばず、ユーザーに確認する
- repo 内の文書・画像には相対リンクを使う。リンク文言は参照先の内容を示す

## 見た目と完了確認

ロゴとバッジは基本的に入れる。既存ロゴを優先し、未用意ならプロジェクト名のシンプルなワードマークを用意する。画像は repo 内で管理し、代替テキストを付け、ライト・ダークの背景で読めるものにする。

- バッジは CI、公開バージョン、ライセンス、ドキュメントなど、実在して読者の判断に役立つものを選ぶ。色とスタイルを揃え、クリック先は実行結果・配布先・利用条件などの詳細にする
- 動的バッジは実際の repo・ブランチ・workflow・パッケージを指定する。雛形の値や固定の「passing」を残さない。外部から取得できない private repo の状態を公開バッジにしない
- CI や公開パッケージが無ければ、そのバッジは省く。バッジを埋めるために未使用の CI やサービスを導入しない
- 中央寄せやロゴのサイズ調整に必要なら最小限の HTML を使ってよい。本文は通常の Markdown とし、狭い画面でも読める構成にする
- 手書きの目次は任意。GitHub には見出しから生成される目次があるため、長さや掲載先に応じて選ぶ

完成前に次を確認する。

- 使う理由・実例・試す導線を保ったまま、さらに削れる文章や節がない
- 冒頭だけで、対象読者の困りごと、得られる結果、このプロジェクトを選ぶ理由、重要な制約が分かる
- デモ・利用例がその価値を裏付け、読者が次に何を試せばよいか分かる。ロゴ・バッジの見た目や機能一覧だけで価値の説明を済ませていない
- 主要読者が最初の操作を完了し、成功を判断できる
- コマンドと利用例が現行の設定・実装と一致している
- 実行可能な手順は、記載したとおりに確認する
- 認証や外部環境が必要で実行できない部分は、作業報告に記載する
- 検証のために、本番への適用やデプロイを行わない
- repo 内のリンク先・画像・見出しアンカーが存在し、掲載先でコードや画像が読みやすく表示される
- ロゴが背景に埋もれず、バッジの対象とクリック先が正しく、取得できない画像や状態が残っていない
- License 節とバッジが確認済みのライセンスと一致し、本文へのリンクが正しい。採用するライセンスがない場合は両方を省いている
- 英語を基準にするプロジェクトでは、日本語版と相互リンクがあり、両方の内容が一致している
- 不要な節、未置換のプレースホルダー、古い手順、未実装機能の断定が残っていない
