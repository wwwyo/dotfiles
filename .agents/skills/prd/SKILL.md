# PRD

PRDは、なぜ作るかと、利用者が何をできるようになるかを合意する文書。実装方法は決めない。目的・主要要件・受入条件を短くつなぎ、枝葉の仕様で選択肢を狭めない。

## 書く範囲

- 課題、対象の利用者、期待する変化、スコープを書く。
- 受入条件は「誰が何をして、どんな結果を得られるか」を検証できる粒度にする。操作手順や網羅的な例外一覧にはしない。
- 費用・プライバシー・性能など、成立に必要な制約だけを残す。合意済みの上限などは書くが、未検証の閾値を埋めない。
- 整理したドメインの概念・関係・ルールはPRDに残す。図は理解に役立つ場合に使い、実装の型・データ構造・状態遷移へ展開しない。
- API、アルゴリズム、タイマー値、送信形式、詳細な評価手順などは必要ならDDや検証記録に分ける。技術候補は参考として示せるが、要件と混ぜない。

## 進め方

1. 依頼と既存のStory・PRDを読み、同じ課題なら既存PRDを更新する。関連するPRDへリンクする。
2. 判断に必要な不明点だけ確認する。十分な文脈があれば質問やヒアリングを繰り返さない。課題が曖昧なら `grill-with-docs`、Storyを新たに整理するなら [story-format](references/story-format.md) を使う。
3. [prd-format](references/prd-format.md) と [雛形](templates/prd.md) を参考に、必要な節だけ書く。解の形が不明で触ると判断できる場合は `prototype` を使う。既に形が決まっている場合や文章で判断できる場合は、試作品や複数案を必須にしない。
4. 目的と要件の整合性、受入条件の検証可能性、howへの踏み込み、冗長さを見直す。複雑な要件や重要な変更では `delegate` で内容・文章の独立レビューを受ける。
5. 必要な判断が済み、実装に進められる要件になったら `status: ready` にする。未解決の重要な判断は未決と明記し、`draft` を保つ。

このskillでは実装を始めない。実装は `implement`、実装の設計書は `document`、用語の整理は `domain-modeling` を使う。

## 置き場と状態

- 既存の置き場と言語に合わせる。新設時は共有文書なら `docs`、個人の下書きならgitignoreされた `.agent` を使う。共有範囲が不明な場合だけ確認する。
- PRDは `<base>/prd/<topic>/prd.md`、必要なDDは同じ場所の `dd.md`、ADRは `<base>/adr/` に置く。topicは短いkebab-caseにする。
- 英語を標準とするPJでは `prd.md` を英語、`prd.ja.md` を日本語で書き、相互リンクと要件・状態を揃える。
- 機能固有の語はPRDのGlossaryに置く。複数機能で使う実体の名詞だけ、repo root `AGENTS.md` のGlossaryにも置く。Storyはプロダクトに一つ。
- 判断に使った試作品は `<base>/prd/<topic>/prototype/` に残す。容量や権利のため除外したものはREADMEに再現方法を書く。本番コードへの移植は行わない。
- 戻すのが難しい判断はADR、スコープ外はNon-Goalsへ残す。戻せる案の履歴をPRD本文に積み上げない。
- `draft` は要件整理中、`ready` は実装可能、`in-progress` は実装中、`done` は要件全体の実装・検証完了。実装側が後二つを更新する。
