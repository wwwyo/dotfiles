# PRD Format

[雛形](../templates/prd.md)は出発点。節を埋めるために情報を増やさず、機能の判断に必要なものだけ残す。置き場・言語は [prd skill](../SKILL.md) に従う。

## 内容

- **Problem** — 誰が何に困っていて、なぜ解決するか。
- **導出** — Storyとの関係。既存の目的から自然に読める場合は短くまとめる。
- **Overview / Goals / Non-Goals** — 利用者の体験と期待する変化、スコープの境界。
- **Acceptance Criteria** — 誰が何をして、どんな結果を得られるか。主要な振る舞いを検証できる条件として書く。実装手順や細かな画面仕様を列挙しない。
- **Non-Functional Requirements** — 成立に重要な制約がある場合だけ書く。数値は合意済みで判定に必要なものに限る。未決の実装パラメータを要件にしない。
- **Success Metrics** — 期待する変化を何で確かめるか。実際のコアアクションや継続利用など、目的に合う指標を選ぶ。測定期間・集計仕様・実験手順は必要なら別の検証記録へ置く。
- **Glossary / Domain Model** — 整理した用語・概念・関係・境界・ルールがある場合に残す。文章、図、表から理解しやすい表現を選ぶ。実装の型やDB schemaへ展開しない。重要な未決事項は明示する。

既存の関連PRDへリンクする。必要に応じてMigrationなどの節を足してよいが、網羅するためには足さない。日本語本文は `japanese-tech-writing` を参考にする。

## 書き分け

PRDは目的と要求する結果を扱う。アルゴリズム、API、具体的なタイマーやデータ構造などのhowはDDへ、試行条件や測定手順は検証記録へ分ける。候補方式は参考として置けるが、必要性が確定していないものを必須要件にしない。

検証そのものが目的のPRDでも、何を学び、何を判断できれば完了かを中心に書く。Go/Killの詳細な閾値・分母・試行回数などは、実行前に検証計画で決める。検証のGoは本番化の許可を意味しない。

## status

先頭のYAML frontmatterに状態を持たせる。

- `draft` — 要件整理中。重要な判断が未解決。
- `ready` — 要件の見直しを終え、実装に進められる。
- `in-progress` — 実装中。
- `done` — 要件全体の実装・検証が完了。

`ready`は実装や受入条件の達成を意味しない。PRDの作成側が `draft` → `ready` を、実装側が `in-progress` と `done` を更新する。部分実装・未検証が残れば `in-progress` のままにする。状態がない既存PRDは `draft` 相当として扱う。
